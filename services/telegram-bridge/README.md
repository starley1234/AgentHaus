# telegram-bridge — двусторонний Telegram-бот

Владелец пишет боту в Telegram → мост создаёт диалог на едином бэкенде
(agent-server), отвечает «👀 Принял, работаю…», по завершении присылает
финальный ответ агента в чат. **Reply** на сообщение бота продолжает тот же
диалог. Транспорт — long polling `getUpdates`: публичный URL и TLS не нужны,
работает за NAT/WSL.

## Запуск

**Ничего запускать не нужно.** Мост стартует автоматически внутри контейнера
вместе со всем стеком, как только в `.env` заполнены `TELEGRAM_BOT_TOKEN` и
`TELEGRAM_CHAT_ID`:

```bash
docker compose up -d --build   # один раз пересобрать; дальше просто up -d
docker compose logs | grep Telegram   # → «Telegram-мост запущен (long polling…)»
```

Несколько получателей: `TELEGRAM_ALLOWED_CHAT_IDS=111,222` в `.env`.

Отдельный запуск на хосте нужен только для разработки:

```bash
./services/run.sh telegram-bridge   # автономно на :8294 (не одновременно с контейнерным!)
```

## Поведение

| Действие в Telegram | Реакция моста |
|---|---|
| обычное сообщение | новый диалог агента; по завершении — ответ в чат |
| сообщение, пока задача выполняется | досылается в текущий диалог |
| reply на сообщение бота | продолжает привязанный к нему диалог |
| `/new` | следующее сообщение начнёт новый диалог |
| `/status` | статус текущего диалога |
| `/stop` | пауза текущего диалога (reply возобновит) |
| `/help`, `/start` | справка |
| файл/фото | пока не принимаются (мост попросит текст) |

## Диагностика: «пишу боту — ничего не происходит»

Проверь по порядку (все команды — на хосте):

```bash
# 1. Мост вообще стартовал?
docker compose logs | grep -i "telegram"
#   «Telegram-мост запущен…»      → идём дальше
#   «Telegram-мост не запущен…»   → в .env пустые TELEGRAM_BOT_TOKEN/TELEGRAM_CHAT_ID
#   ничего                        → образ старый: git pull && docker compose up -d --build

# 2. Переменные дошли до контейнера?
docker exec agenthaus sh -c 'env | grep TELEGRAM'

# 3. Что говорит сам мост?
docker exec agenthaus curl -s http://127.0.0.1:8294/api/status
#   configured:false → пустые переменные;  polling:false / last_error → читай ошибку
#   (например 401 от Telegram = неверный токен; conflict = второй потребитель getUpdates)

# 4. Правильный ли chat_id? Сравни с тем, что видит бот:
docker exec agenthaus notify chatid
```

Типовые причины:
- **перезапуск без пересборки** — мост появился в образе недавно: нужен
  `docker compose up -d --build`, а не просто restart;
- **TELEGRAM_CHAT_ID не заполнен или не твой** — возьми из `notify chatid`;
- **бот отвечает ⚠️-ошибкой** — читай текст: там причина (обычно LLM-профиль
  не настроен в Canvas или agent-server ещё поднимается).

## Безопасность

- **Allowlist**: обрабатываются только чаты из `TELEGRAM_CHAT_ID` /
  `TELEGRAM_ALLOWED_CHAT_IDS`; чужим бот не отвечает вовсе.
- Лимит новых диалогов: `max_new_dialogs_per_hour` в `config.json` (12).
- Диалоги создаются с `confirmation_policy: NeverConfirm` и лимитом
  `max_iterations` (100) — настраивается в `config.json`.
- Токен маскируется в логах и сообщениях об ошибках.

## Состояние

Состояние (offset getUpdates, привязки «сообщение бота → диалог», счётчик
запусков) хранится в json-файле и переживает перезапуск: в контейнере —
`~/.openhands/agent-canvas/telegram-bridge-state.json`, при запуске на хосте —
`state.json` рядом с сервисом (в .gitignore).

## Координация с `notify ask` — автоматическая

Telegram отдаёт каждое обновление только одному потребителю getUpdates,
поэтому мост и `notify ask` договариваются сами, настраивать ничего не надо:

- мост пишет heartbeat-файл; живой мост = владелец getUpdates;
- `notify ask` видит свежий heartbeat → не трогает getUpdates, а ждёт ответ
  через relay-файл моста;
- мост видит lock активного `ask` → сообщения владельца не превращает в
  задачи, а ретранслирует в relay-файл для `ask`.

Единственное реальное ограничение: не держи ДВА экземпляра моста
(контейнерный + хостовый) одновременно.
