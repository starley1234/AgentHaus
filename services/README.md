# Сервисы (mini-frontends) — независимые приложения поверх единого бэкенда

Здесь живут **независимые сервисы** — маленькие, заточенные под одну функцию
приложения (например «написать книгу и опубликовать её как сайт»). Каждый
сервис — это самодостаточный пакет в собственной папке (`services/<имя>/`) со
своим:

- **конфигом сервиса** (`config.json`) — какие скиллы, MCP-серверы, модель,
  сценарий/промпт и порт (для автономного запуска) использовать;
- **прослойкой-бэкендом сервиса** (`server.mjs`) — тонким хендлером, который
  говорит с **единым бэкендом** (agent-server) и отдаёт готовый результат;
- **тонким фронтендом** (`web/`) — голый минимальный UI, который общается
  только со своим сервисом, а не с единым бэкендом напрямую.

## Архитектура: один шлюз, один порт, много путей

Вместо того чтобы держать сотни Node-процессов и сотни портов, **все сервисы
монтируются на одном порту через единый шлюз** (`services/gateway.mjs`):

```
┌──────────────┐  HTTP   ┌────────────────────────────────────────┐
│ Тонкий        │ ──────► │ ШЛЮЗ (gateway.mjs) — один порт 8290     │
│ фронтенд      │ ◄────── │  /                   → список сервисов  │
│ (web/)        │         │  /book-site/         → сервис book-site │
└──────────────┘         │  /debate/             → сервис debate    │
                         │  ... любой сервис из services/          │
                         └──────────┬──────────────────────────────┘
                                    │ createApp() → HTTP-хендлер
                                    ▼
                         ┌──────────────────────┐
                         │  ЕДИНЫЙ БЭКЕНД        │  (agent-server, неизменный)
                         │  agent-server +       │
                         │  automation + Canvas  │
                         └──────────────────────┘
```

- Каждый `server.mjs` экспортирует `createApp()` → HTTP-хендлер `(req, res)`.
- Шлюз импортирует все сервисы из `services/`, зовёт их `createApp()` и
  монтирует под путём `/<имя>/`.
- При запросе `/<имя>/*` шлюз **срезает префикс** и вызывает хендлер с
  корневым путём (`/api/...`, `/site/...`), поэтому код роутинга внутри
  сервиса одинаков и под шлюзом, и автономно.
- Чтобы один и тот же фронтенд работал и автономно (в корне `/`), и под
  шлюзом (`/<имя>/`), он обязан использовать **относительные пути**:
  `fetch("api/...")` и `href="site/<id>/"`. Браузер резолвит их от текущей
  страницы, так что отдельная настройка basePath не нужна.
- `/имя` (без слэша) шлюз редиректит на `/имя/` (301), иначе относительные
  ссылки резолвились бы от корня.

Ключевые принципы:

1. **Единый бэкенд остаётся единственным источником правды** про агента: он
   выполняет диалоги, держит MCP/скиллы, работает с файлами. Ничего не
   форкаем и не дублируем.
2. **Прослойка-сервис** инкапсулирует *настройки конкретной функции*: какой
   сценарий дать агенту, какие скиллы/MCP включить. Она — единственный, кто
   знает детали; фронтенду их знать не нужно.
3. **Тонкий фронтенд** — максимально простая страница «введите тему → получите
   результат». Он не ходит в agent-server напрямую (не тащит API-ключи,
   настройки, конфиденциальность бэкенда).
4. **Масштабирование**: добавить сервис = положить папку `services/<имя>/` с
   `server.mjs` и `config.json`. Шлюз подхватит его при следующем запуске —
   без новых портов и процессов. Отключить сервис — поставить в `config.json`
   `"enabled": false`.

## Структура одного сервиса

```
services/<имя>/
  config.json      # скиллы, mcp, модель, сценарий, title/description, port
  server.mjs       # экспортирует createApp() → HTTP-хендлер
  web/             # тонкий фронтенд (HTML/JS/CSS), относительные пути
  README.md        # что за функция, как запустить

services/gateway.mjs  # единый шлюз (монтирует все сервисы, один порт)
services/lib/         # общие хелперы
  host.mjs          # loadConfig + bootStandalone (запуск одного сервиса автономно)
  agent-server.mjs  # общение с единым бэкендом (settings + conversations + статус)
  job-manager.mjs   # реестр задач, опрос статуса, сборка сайта в рабочую директорию
  web.mjs           # markdown→HTML, сборщики сайтов, serveStatic
```

## Где оказываются результаты

- Агент пишет исходные файлы в **рабочую директорию диалога** — на хосте это
  `./projects/<service>-<jobId>/` (смонтировано из `/projects` внутри контейнера).
- Сервис собирает из них сайт в подпапку `_site` **той же рабочей директории**,
  поэтому и исходники, и готовый сайт лежат в каталоге проекта (ты их видишь в
  файловой вкладке Canvas / на хосте в `./projects/`).
- Дополнительно сервис публикует сайт по HTTP: под шлюзом это
  `http://localhost:8290/<имя>/site/<jobId>/` (в API возвращается **относительная**
  ссылка `site/<jobId>/`, чтобы работать и автономно, и под шлюзом).

## Контракт прослойки (обязательные endpoints)

Каждый `server.mjs` реализует единый набор маршрутов (относительно корня
сервиса — `/` автономно или `/<имя>/` под шлюзом):

| Маршрут | Описание |
| --- | --- |
| `GET  /` | тонкий фронтенд |
| `GET  /health` | живой ли сервис |
| `POST /api/run` | создать/запустить задачу (тело: входные данные пользователя) → `{ jobId }` |
| `GET  /api/jobs` | список задач (автообновляет running-задачи) |
| `GET  /api/status?id=` | статус одной задачи (running / finished / error) |
| `GET  /api/result?id=` | результат задачи + ссылку и путь к сайту |
| `GET  /site/<jobId>/*` | опубликованный сайт задачи |

Прослойка общается с единым бэкендом через его REST API (создание диалога
`POST /api/conversations`, опрос статуса, чтение файлов проекта), скрывая
детали от фронтенда.

## Как запустить

### Все сервисы через шлюз (рекомендуется)

```bash
# 1. Подними единый бэкенд (если ещё не поднят)
docker compose up -d --build

# 2. Запусти шлюз (один процесс, один порт 8290)
./services/run.sh

# 3. Открой http://localhost:8290/  — стартовая страница со списком сервисов
```

### Один сервис автономно (для разработки)

```bash
./services/run.sh book-site        # на своём порту (config.port)

# или вручную:
cd services/<имя>
AGENT_SERVER_URL=http://localhost:8000 \
AGENT_SERVER_API_KEY=<LOCAL_BACKEND_API_KEY> \
node server.mjs
```

Переменные: `GATEWAY_PORT` (по умолчанию 8290) — порт шлюза;
`AGENT_SERVER_URL`/`AGENT_SERVER_API_KEY` — адрес и ключ единого бэкенда.
Хелпер `services/lib/agent-server.mjs` забирает настройки агента с бэкенда
(`GET /api/settings` с зашифрованными секретами), создаёт диалог и опрашивает
его статус — так сервис не дублирует LLM-ключи и настройки.

Пути: бэкенд видит рабочую директорию как `/projects/...`, сервис читает те же
файлы на хосте как `./projects/...`. Маппинг задаётся `AGENT_WORK_ROOT` (по
умолч. `/projects`) и `HOST_WORK_ROOT`. **`HOST_WORK_ROOT` по умолчанию берётся
из `PROJECTS_PATH` из `.env`** — это та же директория, что монтируется в
`/projects` контейнера. Если их не совпадали, сервис «не видел» файлы агента
(книга/сайт собирались пустыми). Если используешь кастомный `PROJECTS_PATH`
(например WSL `/mnt/d/workflow`), указывать `HOST_WORK_ROOT` вручную не нужно.

## Админ-панель: /admin

Всё управление сервисами — на том же порту шлюза, в `/admin/`:

- **Список сервисов** — name/title, включён ли, доступ, ссылка.
- **Включить/отключить**, **сменить доступ**, **перегенерировать метаданные**
  (перечитывает config.json и переимпортирует хендлер без рестарта шлюза).
- **Автосоздатель сервиса** — форма «опиши сервис»: шлюз генерирует полный
  скелет `services/<имя>/{config.json, server.mjs, web/index.html, README.md}`
  на универсальной прослойке (агент пишет markdown → сайт). Опционально
  сценарий уточняет агент на едином бэкенде (галочка «через общий бэкенд»).
  **Тип ввода** — «текст» или «файл» (фото и т.п.): для файловых сервисов
  фронтенд получает `<input type="file">`, а сервер загружает файл в рабочую
  директорию агента (`/api/file/upload`) до старта диалога, и агент видит его
  как `params.fileName`.

Доступ к админке — только админам (см. RBAC ниже). Пока нет UI логина:
админ-доступ даёт `ADMIN_KEY` (env/`.env`), передаваемый заголовком
`x-admin-key: <ключ>` или cookie `agenthaus_admin`.

## Доступ сервисов (public / registered / admin)

У каждого сервиса в `config.json` поле `access` (по умолчанию `public`):

| access | Кому доступен |
| --- | --- |
| `public` | всем, без авторизации (работает «из коробки») |
| `registered` | любому вошедшему пользователю |
| `admin` | только администратору |

Шлюз проверяет доступ ДО маршрутизации и отдаёт страницу «Нет доступа» (403)
тем, у кого нет прав. Публичные сервисы не тратят время на авторизацию.

## API-ключ сервиса (программный доступ)

У каждого сервиса есть свой `api_key` (в `config.json`, автогенерируется при
первом запуске). Программный доступ к `/api/*` сервиса требует ключ:

```bash
# заголовок
curl -H "x-api-key: <ключ>" http://localhost:8290/<имя>/api/jobs
# или query-параметр
curl "http://localhost:8290/<имя>/api/jobs?api_key=<ключ>"
# или Bearer
curl -H "Authorization: Bearer <ключ>" http://localhost:8290/<имя>/api/jobs
```

Ключ виден в админке (`/admin` → список сервисов). Веб-интерфейс сервиса
подставляет ключ автоматически (инжектится в страницу), поэтому человеку в
браузере ничего вводить не нужно. `/health`, `/site/*` и сама страница — открыты.

> Примечание о безопасности: ключ виден в исходнике страницы локально — для
> личного/локального деплоя это допустимо. Для публичного доступа поверх ключа
> используй `access: registered/admin` и реальную авторизацию.

## RBAC (в стиле Koseven/Kohana) — модель

`services/lib/auth.mjs` проектирует модель прав, совместимую с фреймворком
**Koseven** (форк Kohana), чтобы его можно было «приделать» позже без смены
модели. Таблицы повторяют схему auth-модуля Kohana/Koseven:

```
users        id, username, email, password(hash), logins, last_login, created_at, updated_at
roles        id, name, description
roles_users  user_id, role_id          (join)
user_tokens  id, user_id, user_agent, token, type, created, expires   (сессии/remember)
```

Сейчас хранилище — JSON-файл `./data/auth.json` (роли по умолчанию: `login`,
`admin`, `editor`). При переносе на Koseven те же данные лягут в таблицы БД.
Авторизация **опциональна**: публичные сервисы работают без входа; вход/сессии
появятся на следующей итерации (сейчас — только bootstrap через `ADMIN_KEY`).

## BOM-парсинг: что добавлено в общий бэкенд

Для сервиса `bom-parse` (и любых vision-задач с файлами) добавлено в общий
бэкенд:

1. **poppler-utils** (`pdftoppm`) в Docker-образ — рендер страниц PDF в PNG.
2. **`inspect_image_with_vision` теперь принимает `path`** — абсолютный путь к
   локальному файлу-картинке (а не только `image_index` из последнего
   пользовательского сообщения). Это позволяет агенту вимлить страницы,
   извлечённые из PDF. Файл: `software-agent-sdk/.../tool/builtins/vision_inspect.py`.
3. **Скилл `pdf-bom-extract`** (`extensions/skills/pdf-bom-extract`) — процедура
   «разбей PDF → вимль каждую страницу → собери иерархический JSON + сводку»,
   с рекомендованной схемой `bom.json` (assemblies → parts → поля).

Нужен сохранённый vision-capable LLM-профиль (Settings → LLM), иначе
`inspect_image_with_vision` вернёт «No vision-capable profile available».

## Как добавить новый сервис

1. Скопируйте `services/book-site/` как заготовку в `services/<имя>/`.
2. Заполните `config.json`: `name`, `title`, `description`, скиллы, MCP, модель,
   сценарий, `port` (только для автономного запуска).
3. В `server.mjs` **экспортируйте `createApp()`**, возвращающую HTTP-хендлер.
   Используйте `JobManager` из `../lib/job-manager.mjs`:
   - `promptBuilder(params, jobId)` — собирает промпт и заголовок задачи;
   - `collectResult(job)` — читает файлы из рабочей директории;
   - `buildSite(job, data)` — собирает сайт в `_site` через `buildDocSite`/`buildBookSite`
     из `../lib/web.mjs`.
   Готовый шаблон (createApp + run/jobs/status/result/site) можно скопировать из
   существующего сервиса. В конце файла вызовите
   `await bootStandalone({ importMetaUrl: import.meta.url, createApp })` из
   `../lib/host.mjs` — тогда `node server.mjs` поднимет сервис автономно на
   `config.port`, а шлюз просто импортирует `createApp`.
4. Положите тонкий фронтенд в `web/` **на относительных путях**:
   `fetch("api/...")`, `href="site/<id>/"` — он будет работать и в корне, и под
   шлюзом.
5. Перезапустите шлюз — сервис появится на `http://localhost:8290/<имя>/` и на
   стартовой странице. НОВЫЙ ПОРТ НЕ НУЖЕН.

## Зачем так, а не «вкладки внутри Canvas»

- **Изоляция настроек**: у каждой функции свой сценарий/скиллы/MCP, не
  пересекаются с основным чатом.
- **Голый фронтенд**: юзеру не нужен весь Canvas, чтобы получить книгу или
  сайт — только минимальная страница функции.
- **Один порт / один процесс**: при сотнях сервисов не плодим процессы и не
  упираемся в лимит портов — всё живёт на шлюзе.
- **Корень не захламляется**: все мини-приложения лежат в `services/`, в
  репозитории есть один общий паттерн вместо разрозненных папок в корне.
