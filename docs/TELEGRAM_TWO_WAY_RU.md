# Двусторонний Telegram: проект решения

Статус: **уровень 1 (`notify ask`) и уровень 2 (`telegram-bridge`)
реализованы**. Документ фиксирует архитектуру и способ запуска.

## Текущее положение

```
Диалог Canvas → notify telegram → Bot API → сообщение у владельца   ✅
Владелец отвечает боту → очередь getUpdates (живёт ~24 ч) → НИКТО НЕ ЧИТАЕТ ❌
```

Ответ владельца не теряется мгновенно — он лежит в очереди `getUpdates`
бота, — но ни один компонент его не забирает.

## Уровень 1: «спроси и дождись ответа» — `notify ask` ✅ реализовано

```bash
notify ask --text "Деплоить на прод? (да/нет)" --timeout 1800
```

Как работает (реализация в `extensions/skills/notify/scripts/notify.py`):
1. Отправляет вопрос владельцу (`sendMessage` в `TELEGRAM_CHAT_ID`).
2. Фиксирует текущий `update_id` — всё, что уже лежало в очереди, ответом
   не считается.
3. Длинно опрашивает `getUpdates` (до 25 с на запрос) до `--timeout`
   (по умолчанию 900 с).
4. Принимает **только** сообщения из `TELEGRAM_CHAT_ID` (allowlist),
   чужие игнорирует; полученный ответ подтверждает (offset), чтобы он не
   всплыл повторно.
5. Печатает `ОТВЕТ ВЛАДЕЛЬЦА: …` → агент продолжает работу с учётом ответа.
6. По таймауту — exit code 3 («ответа нет»), агент действует по умолчанию.
7. Параллельные `ask` исключены lock-файлом (`/tmp/agenthaus-notify-ask.lock`,
   протухает через 2 ч).

Свойства:
- работает только пока диалог агента активен — это «уточняющий вопрос
  в мессенджер», а не постоянный бот;
- нулевая новая инфраструктура: тот же stdlib-скрипт, тот же токен.

Сценарии: подтверждение опасных действий («да/нет»), запрос недостающих
данных посреди длинной задачи, «пришли код из СМС».

## Уровень 2: постоянная реакция на входящие (бот-режим)

Три варианта из обсуждения (см. также сравнение ниже):

| | A: cron-автоматизация | B: services/telegram-bridge (long polling) | C: webhook |
|---|---|---|---|
| Задержка реакции | до ~60 с | 1–2 с | мгновенно |
| Публичный URL/TLS | не нужен | не нужен | обязателен (или туннель) |
| Новые процессы | нет (сервис автоматизаций в контейнере) | +1 node-процесс из `services/` | +роут в шлюзе |
| Прецедент в проекте | `slack-channel-monitor` | `services/*` + `lib/agent-server.mjs` | — |
| Подходит для WSL/NAT | ✅ | ✅ | ❌ без туннеля |

Выбранный целевой вариант: **B, с продолжением диалога** — ✅ реализован в
`services/telegram-bridge/` (подробности в его README).

### Запуск моста

**Автоматический**: мост стартует внутри контейнера вместе со всем стеком,
когда в `.env` заполнены `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID`
(достаточно один раз пересобрать: `docker compose up -d --build`).
Проверка: `docker compose logs | grep Telegram`.

Координация с `notify ask` тоже автоматическая (heartbeat + relay-файл,
см. README моста) — Telegram опрашивает только мост, а ответы владельца
для ждущего `ask` он ретранслирует сам. Настраивать ничего не нужно.

Запуск на хосте (`./services/run.sh telegram-bridge`, порт 8294) — только
для разработки, и не одновременно с контейнерным мостом.

### Дизайн telegram-bridge (реализован)

```
Владелец ↔ Bot API ⇄ (long poll) telegram-bridge ⇄ agent-server (/api/conversations)
                          │
                          └── state.json: chat_id+message_thread → conversation_id
```

Поведение:
- **Новое сообщение** (не reply) → новый диалог агента: мост создаёт
  conversation через `services/lib/agent-server.mjs` (настройки LLM берутся
  с единого бэкенда), отвечает «👀 Принял, работаю…».
- **Reply на сообщение бота** → продолжение привязанного диалога
  (`POST события в тот же conversation`) — переписка ощущается как чат
  с агентом.
- **Завершение диалога** → финальный ответ агента уходит в Telegram
  (длинный текст режется, файлы — документами; та же логика, что в notify).
- **Команды**: `/new` — принудительно начать новый диалог; `/status` —
  состояние текущего; `/stop` — остановить выполнение.

Безопасность (обязательные требования):
1. **Allowlist**: обрабатываются только сообщения из `TELEGRAM_CHAT_ID`
   (или списка `TELEGRAM_ALLOWED_CHAT_IDS`). Чужим — молчание (ни ответа,
   ни реакции), чтобы не раскрывать существование бота.
2. **Один активный диалог на чат** + очередь: пока задача выполняется,
   новые сообщения либо продолжают её, либо ставятся в очередь — защита
   от случайной лавины задач и расхода LLM-бюджета.
3. Лимит частоты: не более N новых диалогов в час.
4. Токен и chat_id — из тех же переменных `.env`; мост ничего не логирует
   из содержимого переписки, токен маскируется в ошибках.

Состояние: `state.json` рядом с сервисом (offset getUpdates, привязки
чат→диалог, время последних запусков) — переживает перезапуск моста.

## Что уже возможно сегодня, без изменений

Пока диалог активен, агент может «подождать ответ» и вручную: отправить
вопрос через `notify telegram`, затем опрашивать
`https://api.telegram.org/bot$TELEGRAM_BOT_TOKEN/getUpdates` (curl) и найти
твой ответ. Это работает, но неудобно и не защищено от гонок — поэтому
уровень 1 (`notify ask`) оформляет ровно этот сценарий в одну безопасную
команду.

## Рекомендуемый порядок внедрения

1. **`notify ask`** — ✅ реализовано (подтверждения и уточнения в переписке).
2. **telegram-bridge** — ✅ реализовано («агент в кармане»: писать боту в
   любое время и получать выполненные задачи).
3. Webhook — только при переезде на VPS с доменом (мост поменяет транспорт
   с long polling на webhook, остальное без изменений).
4. Приём файлов через мост (документы из чата → рабочая директория) —
   следующая итерация; пока мост вежливо просит прислать текст.
