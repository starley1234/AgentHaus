# Аудит: cron-автоматизации и внешние коммуникации (август 2026)

Проверка сервиса по запросу владельца: управление cron-задачами (чтобы не
жечь токены на забытых задачах) + поиск проблемных мест в новых компонентах
(notify / telegram-bridge / news-scout / прокси / шлюз сервисов).

## Что добавлено в этом проходе

### 1. Управление cron-задачами — уже есть в UI + новый рубильник

**Управление существующими** автоматизациями в Canvas уже было (страница
**Автоматизации**, `/canvas/automations`): включить/выключить (пауза),
удалить, запустить вручную, отменить бегущий run, посмотреть историю запусков.

**Добавлен глобальный рубильник создания** — `AUTOMATION_ALLOW_CREATE` в
`.env` (по умолчанию `1`):

- `AUTOMATION_ALLOW_CREATE=0` → прокси (static-server) отвечает **403** на
  создание автоматизаций (`POST /api/automation/v1`, `…/uploads`,
  `…/preset/*`) — ни агент, ни UI не смогут завести новую cron-задачу;
- управление существующими (пауза/удаление/запуск/список) **остаётся
  доступным** — можно остановить старую задачу;
- UI показывает баннер на странице «Автоматизации» и отключает кнопки
  «Создать»/«Импорт» (эндпоинт `GET /api/automation-guard`);
- применение: поменять значение в `.env` → `docker compose up -d`
  (пересоздание контейнера, ~секунды, пересборка не нужна).

Рецепт «не сжечь токены»: держи `AUTOMATION_ALLOW_CREATE=0` в обычные дни;
включай на время настройки новой автоматизации.

## Найдено и исправлено

| # | Компонент | Проблема | Исправление |
|---|---|---|---|
| 1 | telegram-bridge | после рестарта моста наблюдение за запущенными диалогами не возобновлялось — финальные ответы никогда не доходили до Telegram | при старте мост перечитывает state и возобновляет watch для всех `running`-диалогов |
| 2 | notify ask | в relay-режиме при смерти моста `ask` ждал до таймаута впустую (getUpdates никто не опрашивал) | обнаружение смерти моста (heartbeat протух) → автоматический переход на прямой опрос getUpdates |
| 3 | notify ask | гонка: ответ, пришедший в момент смерти моста, терялся (baseline брался после него) | в fallback-режиме baseline не берётся, старые сообщения отсекаются по дате |
| 4 | news-scout | рабочая директория могла не существовать в момент создания LLM-диалога (создавалась позже) | `makedirs(STATE_DIR)` в начале запуска |
| 5 | telegram-bridge | `state.json.bindings` рос бесконечно (по записи на каждый ответ бота) | прунинг до 300 последних привязок |
| 6 | Автоматизации | создание cron-задач нельзя было запретить — агент мог завести задачу, о которой владелец забудет | рубильник `AUTOMATION_ALLOW_CREATE` + баннер в UI (см. выше) |

Ранее в этой же серии: ключ agent-server передавался только как
`Authorization: Bearer`, который agent-server не проверяет → все прослойки
не могли создавать диалоги (исправлено: `X-Session-API-Key`); `fetch` моста
игнорировал HTTP(S)_PROXY и IPv6-проблемы (исправлено: свой HTTP-клиент).

## Найдено, задокументировано, НЕ исправлено (осознанно)

| # | Место | Суть | Почему так |
|---|---|---|---|
| 1 | Рубильник создания | обходится изнутри контейнера: бэкенд автоматизаций слушает `127.0.0.1:18001` в том же контейнере, где живёт bash агента — прямой запрос мимо прокси возможен | честный enforcement требует патча pip-пакета `openhands-automation`; SKILL-инструкции ведут агента через прокси (8000), где рубильник работает. Для параноидального режима — правь SKILL.md автоматизаций или вынеси automation в отдельный контейнер |
| 2 | telegram-bridge | сообщение в уже бегущий диалог (`run: true`) может получить 409 от agent-server | мост ловит ошибку и показывает её пользователю ⚠️-сообщением; мягкая очередь сообщений — кандидат на следующую итерацию |
| 3 | telegram-bridge | файлы/фото из чата не принимаются | заявлено в README; уровень 2.1 |
| 4 | notify ask ↔ мост | если мост запущен, но Telegram недоступен (heartbeat свежий, а доставки нет), ask ждёт впустую | вырожденный случай двойного сбоя; таймаут ask отработает штатно |
| 5 | services/gateway | `ADMIN_KEY` пустой → админ-доступ закрыт (fail-closed) — проверено, ок | поведение правильное, оставлено как есть |
| 6 | news-scout | при постоянных отказах LLM дайджест шлётся «самые свежие» без отбора | осознанный fallback: лучше дайджест без ранжирования, чем тишина; отключается `USE_LLM=False` |
| 7 | Дрейф тестов каталога | `test_category_distribution_is_balanced` (design/other) и README-тест (debate, openscad, pdf-bom-extract) падали ДО этой серии изменений | чужой давний дрейф; чинится отдельным PR (добавить 3 README + обновить счётчики) |

## Как управлять процессом (шпаргалка владельца)

```bash
# Посмотреть/остановить cron-задачи: Canvas → Автоматизации
#   тумблер = пауза;  Run now = разовый запуск;  Delete = удалить

# Запретить создание новых cron-задач:
#   .env: AUTOMATION_ALLOW_CREATE=0  →  docker compose up -d

# Проверить, что рубильник активен:
curl -s http://localhost:8000/api/automation-guard   # {"allow_create":false}
```
