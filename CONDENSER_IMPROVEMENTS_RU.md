# Конденсатор контекста: что сделано и как можно улучшить

Дата: 2026-09-11
Ветка: arena/01a08f22-agenthaus
Область: страница настроек `Настройки → Конденсатор` (`/canvas/settings/condenser`),
SDK (`software-agent-sdk/openhands-sdk/.../settings/model.py`, `.../context/condenser/`)

## 1. Что реализовано в этой ветке

### 1.1 Выбор LLM-профиля для конденсации

- В SDK у `LLMSummarizingCondenserSettings` появилось поле `condenser.llm_profile`:
  имя сохранённого LLM-профиля (тот же стор, что использует тул `switch_llm`).
- **Пусто (по умолчанию) = используется LLM диалога** — прежнее поведение, ничего не ломает.
- Если профиль задан, суммаризация гоняется через дешёвую/быструю модель
  (`usage_id = condenser:<профиль>`), токены и стоимость учитываются отдельно.
- Если профиль удалили после сохранения — конденсор молча откатывается на LLM
  диалога с warning в лог, диалог не падает.
- В UI поле рисуется дропдауном: «LLM диалога (по умолчанию)» + список профилей
  (`Настройки → API-ключи`). «Висячее» имя профиля не прячется, а показывается
  выбранным, чтобы было видно, что сохранено.

### 1.2 Переключение типа конденсера (поле `condenser.condenser_kind`)

Аналог классического OpenHands `[condenser] type = ...`, но на новом SDK:

| Значение | Что делает | Вызовы LLM |
|---|---|---|
| `llm_summarizing` | Суммаризация старых событий нейросетью (по умолчанию) | Да |
| `recent` | Держит первые `keep_first` событий + последние; середина отбрасывается | Нет |
| `observation_masking` | Не удаляет шаги: подменяет длинные выводы инструментов (старее последних `keep_latest`) краткой пометкой | Нет |
| `pipeline` | Гибрид: сначала маскирование старых выводов, затем суммаризация, если всё ещё тесно | Почти нет |
| `no_op` | Ничего не сжимает | Нет |

- `recent` покрывает и старый тип `amortized`: в новой архитектуре «амортизированная»
  конденсация — это то же отбрасывание старых событий, но без персистентного
  удаления (история хранится целиком, усечённое вид пересчитывается на каждом шаге,
  поэтому переключение типа обратно безопасно и обратимо).
- Обрезка в `recent` идёт по `manipulation_indices` — атомарные пары
  «действие → результат» не рвутся пополам (тот же механизм, что у суммаризатора).
- `recent` поддерживает и токен-триггер (`max_tokens`): подсчёт через токенизатор
  модели диалога, без completion-вызовов.
- `observation_masking` сохраняет структуру диалога (tool_call ↔ результат),
  оставляя факт вызова и его аргументы, но прячет громоздкий вывод. Идемпотентно.
- **Кнопка «Сжать сейчас» работает для `recent`**: явный запрос отвечает
  `Condensation`-событием, которое перманентно забывает половину сжимаемой
  истории и корректно снимает флаг запроса (иначе флаг висел бы вечно).
  Для чистого `observation_masking` запрос не обрабатывается (маскирование
  не персистентно) — зато в `pipeline` запрос обрабатывает стадия суммаризации.

### 1.3 Схема и UI

- Поле `condenser_kind` помечено `CRITICAL` — тип выбирается прямо на вкладке
  «Базовые»; остальные параметры сгруппированы по типам через новый синтаксис
  зависимостей `depends_on`: `"condenser.condenser_kind=recent,observation_masking"`.
  Фронтенд понимает и старую булеву форму, и новую `ключ=значение[,значение…]`.
- Метаданные полей в SDK обновлены: у каждого параметра осмысленный label +
  зависимости от типа; `max_size` теперь `MAJOR` (виден на «Дополнительных»).

## 2. Предложения по дальнейшему улучшению

### 2.1 Показывать итог конденсации в UI (средне)

Событие `CondensationEvent` уже приходит в стрим; стоит рисовать в чате
компактную плашку «Сжато N событий + summary» с ссылкой «показать детали».
Сейчас пользователь видит только паузу перед следующим шагом.

### 2.2 Гибридный режим «маскирование + суммаризация» — ✅ реализовано

Новый вариант `condenser_kind = "pipeline"`: `PipelineCondenser` из ступеней
`ObservationMaskingCondenser` (настройки `keep_latest`, `max_chars`) +
`LLMSummarizingCondenser` (настройки `max_size`, `keep_first`, `max_tokens`,
`llm_profile`). Маскирование бесплатно убирает основную массу (длинные выводы
инструментов), суммаризация включается только если контекст всё ещё переполнен —
расход на суммаризацию резко падает. Флаг запроса конденсации пробрасывается
через ступень маскирования, поэтому кнопка «Сжать сейчас» в этом режиме работает.

### 2.3 Токен-based триггер для `recent` — ✅ реализовано

`RecentEventsCondenser` получил `max_tokens`: при превышении бюджет режется до
половины через `get_suffix_length_for_token_reduction` (подсчёт токенизатором
модели диалога, без completion-вызовов). Комбинируется с лимитом по событиям —
берётся более строгое сечение. Для `observation_masking` триггер не нужен:
`max_chars` уже ограничивает длину напрямую.

### 2.4 Ручная конденсация для без-LLM типов — ✅ частично

`RecentEventsCondenser.handles_condensation_requests() = True`: явный запрос
возвращает `Condensation` (перманентно забывает ~половину сжимаемой истории,
снимает флаг; если забывать нечего — пустое подтверждение). Для
`observation_masking` запрос не обрабатывается осознанно: маскирование —
view-локальное преобразование и не может персистентно ответить на запрос
(флаг снимается только `Condensation`-событием). В режиме `pipeline` запрос
обрабатывает стадия суммаризации.

### 2.5 Прогрев cost-информации

Рядом с выбором LLM-профиля конденсации показывать, сколько токенов/денег
съела конденсация в текущем диалоге (метрики уже копятся в `llm_registry`
под `usage_id=condenser*` — нужен только запрос агрегата в UI).

### 2.6 Валидация связки профиль ↔ модель диалога

Если у профиля конденсации контекст меньше, чем у модели диалога, суммаризация
может падать на длинных историях. Настройка сохраняется, но стоит предупреждать
в UI (сравнение `max_input_tokens` профиля и диалога доступно на бэкенде).

### 2.7 Мелочи

- Кнопка «Сбросить настройки конденсера к дефолту» на странице.
- Тултип с примером: «240 событий ≈ N токенов для вашей модели».
- Отдельная страница для `agent_context` уже есть; имеет смысл показать на ней
  связь с конденсором (память vs сжатие), чтобы пользователи не путали их.
